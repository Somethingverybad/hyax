# План ускорения клиента (октябрь 2026)

Цель — отклик уровня Telegram на слабых Android (Samsung A13, Huawei с Chromium 92)
и в Electron. Замеры — Chrome remote debugging на A13: время до первого кадра,
кадры при прокрутке ленты, время переключения вкладок. Шаги упорядочены по
выигрышу на единицу риска; каждый — отдельный коммит и OTA, с замером до/после.

## Точка отсчёта — Redmi 2409BRN2CG (Android 16, Google Play 774, сборка 835), 23.10.2026
Снято через DevTools Protocol по USB (scratchpad: perf2/perf3/cold.mjs).
- Переключение вкладок, окно 1,2 с после тапа: контент через 280–610 мс
  (Стена 280, список 330–490, Избранное 560–610); кадров 27–57 из 72,
  пропущено 14–43; длинные задачи 2–6 на переход, 170–420 мс каждая, самая
  длинная — монтирование переписки Избранного (418 мс). Это главная боль.
- Прокрутка Стены (20 постов, 48 картинок) и Избранного (60 сообщений):
  60 к/с без пропусков, долгих задач нет. На этом телефоне лента не тормозит;
  виртуализация (п. 6) нужна ради слабых устройств и длинных лент.
- Холодный старт: экран приложения через 0,8–1,3 с, первый контент страницы
  через 1,5–2,0 с после её загрузки, список чатов через 3,0–3,7 с от команды
  запуска. Разбор JS основного файла — около половины этого времени.
- Покой: 60 к/с, фоновой нагрузки нет.

### После шага «первый кадр из 24 строк» (сборка 838, тот же Redmi)
- Открытие Избранного из списка ×4: контент через 287–309 мс (было 556–611),
  самая длинная задача 207–230 мс (было 418–422). Суммарно долгих задач за
  1,5 с по-прежнему 500–640 мс — работа разбита на куски, но не уменьшена:
  досборка до 60 строк, применение синхронизации, эффекты. Дальше снижать
  надо саму работу (строка-компонент, отложенные эффекты) и держать недавние
  переписки смонтированными (п. 4), чтобы повторное открытие стоило ноль.
- Возврат в список чатов: до 378–507 мс и задача 200–380 мс — пересборка
  экрана списка при каждом переходе, то же п. 4.

### После живых экранов (сборка 840, тот же Redmi, тёплые переходы)
- Вкладки: контент через 231–377 мс (было 273–610), самая длинная задача
  100–118 мс (было 170–420).
- Открытие Избранного ×4: контент 221–258 мс (835: 556–611), самая длинная
  задача 100–115 мс (835: 418–422), долгих задач суммарно 288–304 мс
  (835: 549–706), пропущено 16–18 кадров из 90 (838: 43–44).
- Первый проход после запуска по-прежнему дорогой (монтирование слоя + чанки):
  его снимет пул недавних переписок и дальнейшая нарезка основного файла.

## 1. Нарезка бандла по экранам — сделано
Основной файл был 2,3 МБ без ленивых маршрутов: разбор и компиляция на слабом
Android при каждом холодном старте. Теперь сразу грузятся только вход, список
чатов и переписка; музыка, профиль, настройки, редакторы, публичные страницы —
по требованию (`React.lazy`), частые экраны подгружаются в простое после старта.

## 2. Один запрос вместо залпа при старте
В логах при запуске: `/profiles/current/` ×3, `/chats/` ×2, `/wall/` ×2 — на
сервере с одним процессом это удваивает время первого кадра. Сделать модуль
дедупликации запросов (один промис на один URL в полёте) и разнести несрочное
(`ice-servers`, `sounds`, Стена) на после первого кадра.

## 3. Строка сообщения — отдельный мемоизированный компонент
Лента рисуется одной функцией на 6000 строк: любое изменение состояния
перерисовывает все сообщения. Вынести строку в `MessageRow` с `React.memo` и
стабильными обработчиками (через ref), чтобы реакция на одном сообщении не
трогала остальные. Это подготовка к п. 6.

## 4. Живые экраны вместо пересоздания — сделано для вкладок чатов
Маршруты /chat, /saved, /wall делят одну обёртку (App.tsx CHAT_TABS), экран
чатов не пересоздаётся; на телефоне список, Избранное и Стена — три слоя
(visibility, inert), смонтированные по мере посещения. На стенде с CPU ×6
самая длинная задача при переключении 80–100 мс (было ~240), удалений узлов
лент — ноль, прокрутка сохраняется. Уход со вкладки чатов закрывает открытую
переписку, как раньше. Дальше: пул из 2–3 последних переписок и «Музыка».

## 5. Медиа без второго хода
Каждая картинка: запрос подписи → загрузка; подпись живёт час, кеш WebView
промахивается. Сервер отдаёт подписанные ссылки сразу в сообщениях (пачкой),
срок — сутки, ссылка стабильна в пределах срока; в сообщении — микропревью
(blurhash / 16px JPEG) для мгновенной заглушки; дисковый кеш картинок по id
файла (Cache Storage), а не по ссылке.

## 6. Виртуализация ленты
После п. 3: окно из ~40 строк вокруг видимой области, остальные — пустые
блоки известной высоты. Трогает якорение прокрутки, переходы к сообщению,
закреп, восстановление позиции — делать с набором Playwright-проверок,
которые уже есть в сессии (центрирование, окно поиска, подгрузка в обе стороны).
Промежуточный вариант для проверки — `content-visibility: auto` на строках;
на Chromium 92 нет `contain-intrinsic-size: auto`, поэтому только как опыт.

## 7. Локальный стор как источник правды
Экраны рисуются из одного стора (чаты, сообщения, профиль), сеть и сокет лишь
пишут в него. Сейчас кеш есть (IndexedDB + память), но каждый экран сам решает,
когда идти в сеть. Объединение убирает дубли запросов и мигания окончательно.

## Мелкое, по пути
- `refreshChats` сравнивает список через `JSON.stringify` всего массива — заменить на сравнение по `updated_at`/`id`.
- Список чатов до 100 КБ: убрать из него участников и лишние поля, оставить то, что нужно строке.
